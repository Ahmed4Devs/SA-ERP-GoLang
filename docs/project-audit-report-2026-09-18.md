# تقرير التدقيق الشامل لمشروع ERP-GO

**تاريخ التدقيق:** 2026-09-18 (Asia/Riyadh)  
**الحالة المدققة:** الفرع `master`، الالتزام `2af2133`، الوسم `v1.0.0`  
**نوع التدقيق:** مراجعة ساكنة للكود والإعدادات والتوثيق، بناء فعلي، اختبارات وحدة وتكامل، تشغيل API على PostgreSQL 18 معزولة، وفحص صور Docker.  
**حدود التدقيق:** هذا فحص هندسي عملي وليس تدقيق امتثال قانوني أو اختبار اختراق أو اعتماد رسمي من ZATCA.

## 1. الملخص التنفيذي

المشروع يحتوي نواة Backend كبيرة ومنظمة نسبيًا، ويغطي معظم مجالات ERP المذكورة في README بقواعد بيانات وخدمات ومسارات HTTP واختبارات تكامل. بناء Go، وفحص `go vet`، واختبارات الوحدة، وفحص TypeScript وESLint، وبناء Next.js تنجح محليًا. كما نجحت 27 حزمة من أصل 29 حزمة اختبارات تكامل على PostgreSQL 18 معزولة.

لكن المشروع **غير جاهز للإنتاج بصورته الحالية** للأسباب الجوهرية التالية:

1. صور Docker الخاصة بالـAPI والـworker لا تُبنى بسبب اختلاف إصدار Go، وصورة الويب لا تُبنى بسبب غياب مجلد `public`.
2. أغلب واجهة الويب واجهة عرض ببيانات محلية وليست متصلة بالـAPI؛ الاتصال الفعلي موجود فقط لتسجيل الدخول ولوحة المعلومات.
3. قاعدة بيانات جديدة لا تحتوي مرجع العملة `SAR`، ما يعطل العمليات ذات المفاتيح الأجنبية في المحاسبة والميزانيات.
4. تهيئة الخزينة عند تشغيل الـAPI تفشل بسبب SQL يشير إلى `EXCLUDED.name_ar` في جدول لا يحتوي هذا العمود.
5. تكامل ZATCA الافتراضي محاكي، والتوقيع يحتوي fallback وهميًا؛ لذلك لا يصح اعتبار النظام متوافقًا إنتاجيًا مع المرحلة الثانية حاليًا.
6. بيانات اعتماد مدير افتراضية ثابتة تُنشأ حتى في الإنتاج، وعزل المستأجر في middleware لا يتحقق من صلاحية المستخدم على الكيان القانوني المطلوب.
7. الـworker وRedis والبريد الفعلي والتخزين الدائم ليست موصولة تشغيليًا كما يوحي التوثيق.

**التقييم الإجمالي:** أساس Backend واعد وقابل للتطوير، لكن الحالة الحالية أقرب إلى **نموذج وظيفي متقدم / pre-production** وليست إصدارًا إنتاجيًا مكتملًا.

### تفاصيل فشل اختبارات التكامل

- حزمة `accounting`: عند تشغيل المجموعة كاملة تبدأ قبل تطبيق migrations، فتفشل 12 حالة لأن جداول `organization` غير موجودة. وعند إعادة تشغيلها بعد تطبيق migrations، تفشل عمليات القيود بسبب غياب `SAR`، وينتهي أحد الاختبارات بـnil pointer panic. هذا يثبت أن الاختبارات تعتمد على ترتيب وحالة قاعدة مشتركة وليست معزولة.
- حزمة `budgeting`: تفشل 4 حالات لأن `budgets.currency_code='SAR'` يشير إلى `ref.currencies` الفارغ.
- بقية حزم التكامل الـ27 نجحت، وتشمل IAM والتنظيم والتفويض والتدقيق وسير العمل والضرائب والمنتجات والمخزون والمبيعات والمشتريات والمدينين والدائنين والبنوك والموارد البشرية والحضور والإجازات والرواتب وGOSI والأصول والوثائق والإشعارات والتقارير ولوحة المعلومات وZATCA بالمحاكي.

## 4. ما يعمل حاليًا

### Backend وقاعدة البيانات

- الهيكل Modular Monolith واضح، مع فصل domain/application/ports/infrastructure/transport في أغلب الوحدات.
- كل حزم Go تُبنى، و`go vet` ناجح.
- migrations كلها قابلة للتطبيق على PostgreSQL 18 جديدة وتصل إلى الإصدار 270.
- توجد طبقة SQL مولدة بـsqlc وعدد كبير من الاستعلامات الفعلية، وليست الواجهة الخلفية مجرد stubs.
- المصادقة الأساسية تعمل باستخدام Argon2id، جلسات عشوائية مخزنة كhash، وcookie من نوع HttpOnly وSecure في production.
- المسارات المحمية تعيد 401 دون جلسة، وتم التحقق من login و`/auth/me` فعليًا.
- health، readiness، Prometheus metrics، logging، recovery، body limit، CORS، CSRF، وrate limiting موجودة ومختبرة جزئيًا.
- قواعد القيد المزدوج وعدم تعديل القيود المرحلة موجودة في الخدمة وقاعدة البيانات، مع decimal exact arithmetic وعدم وجود أنواع FLOAT/REAL في المخطط.
- وظائف واسعة للمبيعات والمشتريات والمخزون والرواتب والضرائب والتقارير وغيرها مدعومة باختبارات تكامل ناجحة.
- CLI الخاص بـ`migrate up` و`version` يعمل.

### واجهة الويب

- Next.js 15 وReact 19 وTypeScript تُبنى بنجاح.
- 30 صفحة ومساحات عمل كثيرة متوفرة بصريًا.
- دعم العربية/الإنجليزية وRTL/LTR والثيم الفاتح/الداكن موجود.
- شاشة الدخول تتصل فعليًا بخدمة المصادقة، ولوحة المعلومات تحاول جلب بيانات حقيقية.
- المكونات والتصميم متماسكة، ولا توجد أخطاء TypeScript أو ESLint وقت الفحص.

### التشغيل والتوثيق

- توجد ملفات Compose للتطوير والإنتاج، Nginx، health checks، صور متعددة المراحل، وأدلة تشغيل ونسخ احتياطي واستعادة وترقية.
- إعداد Compose بنيويًا صالح، وصورة migrations قابلة للبناء.
- توجد 3 قرارات معمارية ADR ودليل معماري وتشغيلي.

## 5. ما لا يعمل أو يعمل جزئيًا

### 5.1 حواجز حرجة تمنع النشر الإنتاجي

#### أ. صور API والـworker لا تُبنى

- `go.mod` يطلب `go 1.27.1`.
- `deployments/docker/Dockerfile.api` و`Dockerfile.worker` مبنيان على `golang:1.24-alpine`.
- الفشل الفعلي: `go.mod requires go >= 1.27.1 (running go 1.24.13)`.

#### ب. صورة الويب لا تُبنى

- كلا Dockerfile للويب ينسخ `/app/public` في مرحلة التشغيل.
- لا يوجد `apps/web/public` في المستودع.
- بناء Next نفسه ينجح، ثم يفشل Docker عند خطوة `COPY`.

#### ج. Compose التطوير لا يطبق migrations

- `docker-compose.yml` يشغل PostgreSQL ثم API مباشرة ولا يحتوي خدمة migrate.
- على قاعدة جديدة، API يتصل بقاعدة فارغة ثم يحاول seeding على جداول غير موجودة؛ النتيجة خدمة تبدو حية لكن وظائف المجالات تفشل.

#### د. أوامر README لا تطابق Compose

- README يستخدم قاعدة `erp_db` وكلمة مرور `erp_pass`.
- Compose التطوير يستخدم `erp_dev` و`erp_secret_password`.
- الأمر المنشور فشل كما هو بسبب بيانات الاعتماد.

### 5.2 أخطاء قاعدة البيانات والتهيئة

#### أ. العملة المرجعية مفقودة

`000001_reference.sql` ينشئ جدولي العملات والدول لكنه لا يضيف أي صفوف. وحدات لاحقة تفترض وجود `SAR`، وبعضها يملك FK صريحًا إليه. الأثر المثبت:

- فشل إنشاء القيود المحاسبية ذات العملة.
- فشل إنشاء وتهيئة الميزانيات.
- نجاح migration لا يعني أن قاعدة البيانات جاهزة للعمل.

#### ب. seed الخزينة معطوب

الإجراء في `000160_treasury_banking.sql` ينفذ `SET name_ar = EXCLUDED.name_ar` أثناء upsert على `banking.bank_accounts`، بينما اسم العمود هو `bank_name_ar`. تشغيل API أعطى:

`ERROR: column excluded.name_ar does not exist (SQLSTATE 42703)`

#### ج. أخطاء seed لا تمنع الإقلاع أو الجاهزية

الخادم يسجل أخطاء seed كتحذيرات ويكمل. `/readyz` أعاد `UP` رغم فشل تهيئة الخزينة والميزانيات. والأسوأ: إذا فشل إنشاء pool بالكامل، لا يُضاف checker للقاعدة وتظل readiness قابلة لإرجاع `UP` بينما كل وحدات الأعمال غير مركبة.

### 5.3 واجهة الويب ليست متكاملة وظيفيًا

- البحث في كامل `apps/web` وجد استدعاءي `fetch` فقط: login وdashboard.
- بقية الشاشات تعتمد arrays محلية وstate داخل React؛ أزرار الإنشاء والتعديل والاعتماد غالبًا تغيّر العرض المحلي ولا تحفظ في Backend.
- توجد بيانات mock/initial صريحة في المحاسبة والتدقيق والوثائق والإشعارات وسير العمل ولوحة المعلومات، إضافة إلى بيانات ثابتة في بقية الملفات الكبيرة.
- لا توجد اختبارات frontend نهائيًا، لا unit ولا component ولا E2E.
- لا يوجد route guard في Next.js؛ يمكن فتح الصفحات المحمية وعرض بياناتها التجريبية دون تسجيل الدخول، رغم أن Backend نفسه يتطلب جلسة.
- dashboard يخفي فشل الشبكة بصمت ويعرض البيانات الافتراضية، ما قد يوهم المستخدم أن الأرقام حقيقية.
- روابط تنزيل الوثائق تستخدم `legal_entity_id` صفريًا ثابتًا.
- تسجيل الدخول يستخدم `NEXT_PUBLIC_API_URL` أو `http://localhost:8080`. إعداد الإنتاج لا يمرر هذه القيمة وقت بناء الواجهة، فيحاول متصفح المستخدم الاتصال بـlocalhost عبر HTTP بدل نفس نطاق Nginx، وقد يصطدم أيضًا بـmixed content.

### 5.4 ZATCA ليست جاهزة للإنتاج

- `zatca.NewModule` يختار `SimulatorClient` دائمًا، ولا يربط `HTTPClient` الحقيقي بناءً على البيئة.
- migrations تزرع secret باسم `mock-zatca-api-secret-2026`.
- التوقيع يرجع قيمًا وهمية ثابتة إذا تعذر فك المفتاح بدل إيقاف العملية.
- دالة hash تصف نفسها بأنها canonical XML hashing لكنها تحسب SHA-256 للنص الخام دون canonicalization مطبق.
- التوقيع يستخدم P-256 بينما التعليق يقول secp256k1 أو P-256، ولا توجد سلسلة تحقق واعتماد إنتاجية مثبتة.
- RetryWorker يُنشأ داخل وحدة ZATCA لكنه لا يُشغل من `erp-api` أو `erp-worker`.
- نجاح اختبارات ZATCA الحالي يثبت منطق المحاكي، وليس قبول منصة FATOORA الحقيقية.

بالتالي عبارة “ZATCA Phase 2 Compliant” في README غير مثبتة ويجب اعتبارها ادعاءً سابقًا لأوانه حتى نجاح اختبارات المطابقة والتكامل الرسمية.

### 5.5 الـworker وRedis والإشعارات والتخزين

- `erp-worker` عبارة عن ticker وheartbeat فقط، ولا يستهلك jobs ولا يشغل ZATCA retries أو outbox.
- Redis موجود في Compose الإنتاج، لكن لا يوجد Redis client في Go ولا قراءة لـ`REDIS_URL`؛ لا cache ولا queue موزعة فعليًا.
- API يستخدم `NewMockMailer()` حتى في الإنتاج. SMTPMailer موجود لكنه غير موصول بالإعداد أو bootstrapping؛ الرسائل “المرسلة” تبقى في الذاكرة وتضيع عند إعادة التشغيل.
- تخزين الوثائق محلي في `./data/storage`، لكن Compose الإنتاج لا يركب volume لهذا المسار داخل API؛ الملفات تضيع عند استبدال الحاوية ولا يمكن مشاركتها بين نسخ API متعددة.
- OpenTelemetry ينشئ tracer provider محليًا بلا exporter؛ لا يتم إرسال traces إلى collector.

### 5.6 الأمن وعزل المستأجر

#### نقاط جيدة

- Argon2id، session hashing، HttpOnly cookies، security headers، limits، audit schemas، واختبارات أمن أساسية موجودة.

#### فجوات حرجة

- التطبيق يزرع حساب `admin / Admin@ERP123!` تلقائيًا، بما في ذلك `APP_ENV=production`، والواجهة تعرض كلمة المرور الافتراضية.
- إعداد الإنتاج يحتوي كلمات مرور وقيم secrets افتراضية قابلة للتشغيل. التحقق من config لا يرفضها في production.
- متغيرات `SESSION_SECRET` و`JWT_SECRET` و`CSRF_SECRET` و`CORS_ALLOWED_ORIGINS` و`REDIS_URL` المعلنة في Compose ليست مقروءة من كود config الحالي.
- `TenantBoundaryGuard` يتحقق فقط أن `legal_entity_id` UUID صالح ثم يضعه في context؛ لا يتحقق أن المستخدم المصادق عضو أو مخول على هذا الكيان. ومعظم الوحدات تركب middleware المصادقة فقط، لا middleware تفويض صلاحيات لكل عملية. هذا يترك مخاطرة IDOR/tenant escape تحتاج اختبارًا وتصحيحًا عاجلًا.
- rate limiter داخل ذاكرة كل instance ويثق بأول قيمة في `X-Forwarded-For`؛ يمكن تجاوزه عبر تعدد النسخ أو header spoofing إذا لم يُحكم proxy chain.
- MFA موجود كجدول فقط؛ لا توجد خدمة أو enrollment أو challenge أو مسارات MFA، رغم ادعاء README ووجود خيار شكلي في settings.
- `/metrics` متاح دون حماية، ويستخدم المسار الخام label رغم تعليق “sanitize”، ما يسبب high-cardinality عند وجود UUIDs في URLs.

### 5.7 التوثيق وOpenAPI غير متزامنين مع التنفيذ

- OpenAPI يوثق 39 path فقط مقابل نحو 377 تسجيل route في الكود.
- أمثلة تعارض واضحة:
  - الموثق `/api/v1/organizations`، والمنفذ تحت `/api/v1/org`.
  - الموثق `/api/v1/sales/customers`، والمنفذ `/api/v1/receivables/customers`.
  - الموثق `/api/v1/purchasing/suppliers`، والمنفذ `/api/v1/payables/suppliers`.
  - الموثق `/api/v1/fixed-assets/...`، والمنفذ `/api/v1/fixedassets/...`.
  - الموثق `/api/v1/workflows/...`، والمنفذ `/api/v1/workflow/...`.
- README والوسم يقولان v1.0.0، بينما config وAPI وCLI و`package.json` تعيد 0.1.0.
- README يَعِد `NUMERIC(24,6)`، بينما المخطط يستخدم غالبًا `NUMERIC(18,4)` ومقاسات أخرى.
- README يذكر MFA وRedis/cache/queues وZATCA production-grade، بينما التنفيذ الحالي لا يحققها كاملة.
- `apps/web/go.mod` ملف Go وهمي غير مستخدم داخل مشروع Next.js ويزيد الالتباس.

### 5.8 الاختبارات وجودة التسليم

- لا توجد CI/CD configuration في المستودع.
- الاختبارات التكاملية تتشارك قاعدة واحدة، وبعض suites تنفذ `MigrateDown` داخل الإعداد؛ لذلك تعتمد النتائج على الترتيب ولا تصلح للتوازي بأمان.
- حزمة المحاسبة لا تطبق migrations في setup أصلًا.
- لا توجد اختبارات واجهة أو browser E2E ولا contract tests بين الويب والـAPI/OpenAPI.
- معظم اختبارات المجال موجودة خارج الحزم تحت `tests/integration`؛ تقرير `go test -cover ./internal/...` يظهر 0% لمعظم الوحدات، لذلك لا توجد قياسات تغطية موحدة مفيدة حاليًا.
- 63 ملف Go غير منسق بـgofmt.
- `npm audit` كشف ثغرة high في PostCSS المتداخل وثغرة moderate مرتبطة بـNext/PostCSS. الإصلاح المقترح من npm يتطلب قفزة major، لذا يحتاج اختبار ترقية منضبط.
- `next lint` deprecated وسيزال في Next.js 16.

### 5.9 مشاكل التشغيل والنسخ الاحتياطي

- لا يوجد `.dockerignore`؛ من مجلد العمل الحالي تجاوز سياق Docker نحو 890 MB بسبب ملفات ignored مثل `node_modules`، ما يبطئ ويبث ملفات غير لازمة إلى BuildKit.
- Compose الإنتاج يضبط `APP_PORT` بينما التطبيق يقرأ `HTTP_PORT`. يعمل حاليًا بالمصادفة لأن fallback هو 8080.
- Compose يضع fallbacks إنتاجية لكلمات المرور ويضيف localhost إلى CORS حتى في production.
- أداة PowerShell Doctor أعطت نجاحًا كاملًا مع أن Docker builds واختبارات التكامل وseeds معطلة؛ فهي تفحص وجود الملفات والأدوات أكثر من صحة النظام.
- سكربت backup المحلي يستخدم `pg_dump --format=custom --compress=9` لكنه يسمي الملف `.sql.gz`، بينما restore يفترض دائمًا `gunzip | psql`. صيغة custom يجب استعادتها بـ`pg_restore`، لذا هذا المسار غير متوافق.
- عند التشفير، backup يكتب checksum لملف `.enc` في اسم checksum الخاص بالملف قبل التشفير، بينما restore يبحث عن `<encrypted-file>.sha256`؛ التحقق لن يجده.
- الاحتفاظ الافتراضي 30 يومًا لا يحقق وحده ادعاء الاحتفاظ النظامي 6–10 سنوات؛ لا توجد طبقات archive/off-site أو اختبارات restore آلية.
- شهادات Nginx الفعلية غير متتبعة، وهذا صحيح أمنيًا، لكن تشغيل production يحتاج خطوة توليد/تركيب واضحة قبل الإقلاع.

## 7. ما ينقص المشروع، مرتّبًا بالأولوية

### P0 — قبل أي نشر أو بيانات حقيقية

1. إصلاح Docker: توحيد إصدار Go، معالجة غياب `public`، ثم بناء وتشغيل Compose كامل من الصفر.
2. إضافة seed مرجعي موثوق للعملات والدول، وعلى الأقل `SAR`، وإصلاح upsert الخزينة.
3. جعل فشل migrations أو seeds الحرجة يمنع readiness/الإقلاع بدل تسجيل warning فقط.
4. إزالة بيانات المدير الافتراضية من production وفرض secrets حقيقية والتحقق منها عند startup.
5. تطبيق authorization حقيقي يربط المستخدم بالـtenant/legal entity على كل request، مع اختبارات IDOR متعددة المستخدمين.
6. تحويل ZATCA من simulator إلى عميل يختار حسب البيئة، وإزالة fallback التوقيع الوهمي، وتنفيذ canonicalization والتحقق الرسمي.
7. توصيل واجهة الويب بالـAPI الفعلي، إنشاء طبقة client موحدة، auth/session state، route guards، ومعالجة أخطاء واضحة بدل fallback صامت.

### P1 — لإكمال المنتج تشغيليًا

1. تنفيذ worker فعلي لـoutbox وZATCA retry والإشعارات والمهام الدورية.
2. توصيل Redis أو حذفه من الادعاء والتشغيل حتى يصبح مستخدمًا.
3. توصيل SMTP/مزود بريد فعلي واختبارات delivery.
4. إضافة volume دائم للوثائق أو object storage مثل S3/MinIO، مع تشفير وسياسة lifecycle ونسخ احتياطي.
5. إصلاح عزل اختبارات التكامل: قاعدة/schema لكل suite، migrations موحدة، وعدم الاعتماد على ترتيب الحزم.
6. إضافة اختبارات frontend وE2E وAPI contract، وCI إلزامية للبناء والاختبار وlint وsecurity scan وDocker builds.
7. تحديث OpenAPI ليغطي المسارات الفعلية أو توليده آليًا، وإضافة تحقق contract في CI.
8. إصلاح backup/restore وإجراء restore drill آلي موثق.

### P2 — جودة وصيانة

1. تشغيل `gofmt` على الملفات الـ63 وإضافته كفحص CI.
2. معالجة ثغرات npm وترحيل lint إلى ESLint CLI.
3. توحيد رقم الإصدار وبيانات README/config/package.
4. جعل إعدادات CORS/CSRF/HTTP/storage/telemetry/SMTP/Redis مقروءة ومتحققًا منها حسب البيئة.
5. إضافة `.dockerignore` وتثبيت الإصدارات بدل ranges الواسعة حيث يلزم.
6. تحسين metrics labels واستخدام route patterns، وإضافة trace exporter وتنبيهات فعلية.
7. مراجعة ادعاءات “production-grade” و“compliant” في التوثيق حتى وجود أدلة واختبارات اعتماد.

## 8. ترتيب إصلاح مقترح قابل للتنفيذ

1. **اجعل baseline أخضر:** إصلاح `SAR` وseed الخزينة واختبارات accounting/budgeting.
2. **اجعل الحاويات قابلة للبناء:** Go image، مجلد public، `.dockerignore`، ومتغيرات المنفذ.
3. **اجعل الإقلاع صحيحًا:** migrations قبل API في التطوير، وفشل readiness عند غياب DB أو فشل bootstrap.
4. **أغلق المخاطر الأمنية:** admin الافتراضي، secrets، tenant authorization، rate limiting خلف proxy.
5. **اربط الواجهة:** auth guard وAPI client ثم توصيل كل وحدة تدريجيًا مع E2E.
6. **أكمل الخدمات الخلفية:** worker، Redis، SMTP، persistent document storage.
7. **أكمل ZATCA رسميًا:** مفاتيح وشهادات حقيقية، XML canonicalization، signing، onboarding، clearance/reporting، retries، واختبارات sandbox الرسمية.
8. **ثبت التسليم:** CI، Docker smoke test، migration test، backup/restore drill، وتوليد OpenAPI.

## 10. الخلاصة

القيمة الأساسية للمشروع موجودة: نطاق وظيفي واسع، مخطط بيانات كبير، خدمات ومسارات فعلية، واختبارات تكامل كثيرة ينجح معظمها. المشكلة ليست غياب الكود بقدر ما هي وجود فجوة بين **ما يعمل داخل Backend تحت ظروف اختبار محددة** وبين **منتج متكامل قابل للنشر وآمن ومثبت الامتثال**. الأولوية ليست إضافة شاشات جديدة؛ بل تثبيت bootstrap والاختبارات والحاويات والأمان، ثم ربط الواجهة بالخدمات الحقيقية وإكمال التكاملات الخارجية.

لم تُعدّل أي ملفات مصدر أو إعدادات أثناء هذا التدقيق. الملف الوحيد المضاف إلى المشروع هو هذا التقرير.
