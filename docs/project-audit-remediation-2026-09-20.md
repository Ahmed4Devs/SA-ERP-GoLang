# متابعة معالجة تقرير التدقيق — آخر تحديث 2026-09-23

هذه الوثيقة هي الحالة التنفيذية اللاحقة لـ[تقرير التدقيق الأصلي](project-audit-report-2026-09-18.md). التقرير الأصلي محفوظ كسجل لحالة الالتزام `2af2133`، ولا ينبغي قراءة نتائجه القديمة على أنها وصف للحالة الحالية.

## الخلاصة الدقيقة

أُغلقت عيوب الكود القابلة للإصلاح داخل المستودع التي كشفها التقرير، وأضيفت بوابات تمنع رجوعها. اجتاز المشروع بناء Go وNext.js، اختبارات الوحدة والتكامل مع `-race`، تدفقات المتصفح المحاكية، اختبار HTTP حقيقي، فحص عقد OpenAPI، وتجربة نسخ مشفر واستعادة فعلية.

هذا لا يساوي تصريح إطلاق إنتاجي مطلق أو اعتمادًا تنظيميًا. تبقى بنود تشغيلية وخارجية لا يمكن للكود إنشاء أدلتها ذاتيًا: اعتماد ZATCA الحقيقي، أسرار وشهادات المنشأة، جدولة النسخ إلى موقع مستقل، تحديد RPO/RTO واختبارهما على حجم الإنتاج، وبنية تخزين مشتركة إذا كان النشر متعدد المضيفات.

```text
go test -race -count=1 ./internal/...

npm run type-check

```

كما نجح اختبار HTTP حقيقي على PostgreSQL معزولة: تسجيل الدخول، إنشاء فئة منتج ضمن كيان قانوني، قراءتها، التحقق من إنشاء access events وbusiness audit events تلقائيًا، ثم التحقق من سلامة `4/4` سجلات في سلسلة الهاش.

واختُبرت تهيئة PostgreSQL 18.6 من volume فارغ بالمسار الجديد `/var/lib/postgresql` تحت UID غير مميز، وتشغيل Goose ونسخ PostgreSQL المشفر تحت مستخدمين غير root، وفحص إعداد Nginx النهائي مع TLS تجريبي بواسطة `nginx -t`.

## مراجعة 2026-09-23: عزل قاعدة اختبارات التكامل

أظهرت المراجعة أن تشغيل `go test ./...` من دون `TEST_DATABASE_URL` كان يسمح لاختبارات التكامل باستخدام قاعدة `erp_dev` الافتراضية. وبما أن بعض الاختبارات تكتب بيانات وتفرغ جداول، كان هذا مسارًا خطرًا على بيانات التطوير. كما أن تشغيل الحزم بالتوازي استنفد اتصالات PostgreSQL المحلية.

أصبح إنشاء اتصال قاعدة بيانات أو تشغيل migration من داخل اختبار Go يتطلب `TEST_DATABASE_URL` صريحًا ومطابقًا للعنوان المستخدم وبيئة `APP_ENV=testing`. إخفاق إعداد قاعدة التكامل يفشل الاختبار بدل تخطيه. يشغّل هدف `make test` الحزم تسلسليًا، ويوثق README استخدام قاعدة مؤقتة قابلة للإتلاف. وثُبت قفل migrations على اتصال PostgreSQL واحد حتى يبقى فك القفل في الجلسة نفسها.

نجح `go test -race -p 1 -count=1 -timeout 30m ./...` على حاوية PostgreSQL 18.2 مؤقتة مع `TEST_DATABASE_URL` منفصل؛ نجحت حزم التكامل الـ29. كما نجح `go build ./...` و`go vet ./...` وفحص Compose، وفحوص الويب `type-check` و`lint` والاختبارات وبناء الإنتاج. وأثبت اختبار سلبي أن غياب `TEST_DATABASE_URL` يوقف اختبار التكامل برسالة واضحة. أحدث قرار [ADR 0004](adr/0004-postgresql-transactional-outbox.md) توثيق استراتيجية العامل الفعلية.

## بوابات ما قبل الإطلاق الفعلي

لا تُرفع علامة الجاهزية التشغيلية إلا بعد إغلاق البنود التالية في بيئة الجهة المستهدفة:

1. تشغيل onboarding بهوية المنشأة ووحدة EGS وOTP حقيقية، واجتياز حالات الفاتورة والإشعار الدائن والمدين للنوعين القياسي والمبسط على FATOORA، ثم اعتماد مالك الامتثال.
2. إبقاء `ZATCA_ENABLED=false` حتى اكتمال البند السابق، وتوريد `ZATCA_CREDENTIALS_ENCRYPTION_KEY` وبقية الأسرار من secret manager خارج Git.
3. توفير TLS وشهاداته، SMTP حقيقي، DNS، سياسات الشبكة، وحسابات خدمة بأقل صلاحية، ثم اختبارها في staging مطابق للإنتاج.
4. جدولة `erp-backup` خارجيًا، نسخ النتائج المشفرة إلى مخزن مستقل/immutable، تفعيل WAL/PITR إذا تطلب RPO ذلك، وقياس RPO/RTO في تمرين DR على حجم مماثل للإنتاج.
5. استخدام مخزن وثائق مشترك أو object storage قبل أي نشر متعدد المضيفات، وإجراء اختبار failover وعدم فقد الملفات.
6. تنفيذ اختبارات تحميل وسعة، فحص اختراق، تنبيهات ومناوبات فعلية، ومراجعة قانونية لسياسات الاحتفاظ وPDPL وWPS/Qiwa وGOSI.
7. إذا كانت السياسة تتطلب تطابق كل تغيير مجال مع audit event exactly-once، نقل أحداث المجالات المشمولة إلى transactional outbox داخل معاملات تلك المجالات قبل الاعتماد النظامي.

الخلاصة: لا توجد مشكلة مكتشفة مخفية أو ادعاء جاهزية مطلق؛ الإصلاحات داخل المستودع منفذة ومختبرة، والمتبقي معلن كأدلة نشر واعتماد وتشغيل يجب توفيرها في البيئة الحقيقية.
